# impl 命令反馈：小任务分支未产出 tasks.yaml / design，阻断 /adversarial-review 的独立评估

## 触发场景

执行 `/impl "做一个'鸡你太美'的小视频，1分钟左右"` 时，AI 按 `.claude/commands/impl.md` 的 Step 1（复杂度评估）判定为小任务（blast radius = 2：Root.tsx + 新增目录，不涉及既有 composition），直接进入"侦察 → 编码 → lint → commit → record-session"全自动流程。

完成后开发者希望跑 `/adversarial-review` 做独立评估，发现缺少：
- `docs/tasks/{sprint}/tasks.yaml`（Evaluator 机械化执行 verify 断言的唯一来源）
- `docs/design/{name}.md`（Evaluator 判"设计契合度"维度的契约）
- `docs/tasks/{sprint}/iterate-consensus.md`（Evaluator 判"功能性"维度的 desc 来源）

只能事后手工回填。本项目 commit `20ed624` 就是为跑 /adversarial-review 临时回填的 sprint 目录。

## 观察到的问题

**现状（impl.md 现有设计）**：
- 小任务分支：Step 2 侦察 → Step 3 编码 → Step 4 验证 → Step 5 commit → Step 6 record-session（journal / knowledge / checklist / metrics）
- 大任务分支：Step 1 转入 /iterate，由 /iterate 生成 tasks.yaml + checklist.md + design

Step 6 **完全没有**"为小任务生成最小合同"的动作。合同（tasks.yaml）被有意留给大任务作为 *premature closure* 的防护措施。

**问题**：小任务 ≠ 不需要被独立评估。尤其是：
1. **创作型小任务**（视觉设计、文案、UI 微调）：主观空间大，最容易偷懒，最需要 Evaluator 的 D 维度（原创性/避免捷径）盯；
2. **修 bug 类小任务**：Evaluator 本该校验"是否真的解决了问题、还是只在测试里打了补丁"——这正是 adversarial-review 的核心价值，但没有 tasks.yaml 就无从着手；
3. **小任务 commit 累积到发版前**：若没有合同，PR 前的 adversarial-review 只能对大任务有效，小任务的风险被系统性漏掉。

结果是：**小任务成了 harness 评估体系的盲区**。要么人工事后回填（ceremony 并没省，还更痛，因为上下文已凉），要么跳过评估（但那就让小任务永远处在低质量保护下）。

在 `impl.md` 的 Step 6（Record Session）中新增 **6.5 最小合同生成（小任务专属）**，位于 6.4（回写 metrics）之前。

### 生成规则

当 `task_size == "small"` 且本次 commit 成功时，自动生成以下三个文件（若已存在则**追加为第 N 项任务**而非覆盖）：

1. **`docs/tasks/{sprint}/tasks.yaml`** —— 机器可验证断言
2. **`docs/tasks/{sprint}/iterate-consensus.md`** —— 简化版共识（小任务无需完整影响分析，只记目标 + 范围 + 关键决策）
3. **`docs/design/{feature-slug}.md`** —— 单页契约（仅包含必要接口/输出/验收标准）

`{sprint}` 命名规则：`{YYYY-MM}-{feature-slug}`（例如 `2026-04-jntm`）。`{feature-slug}` 从任务描述里提取关键词生成（可让开发者 1 次确认或默认静默取第一个关键词）。

### tasks.yaml 最小模板（小任务版）

```yaml
sprint: {sprint}
design: docs/design/{feature-slug}.md
consensus: docs/tasks/{sprint}/iterate-consensus.md
commit: {short-hash}

tasks:
  - id: T001
    desc: "{从任务描述生成的一句话 desc}"
    status: done
    verify:
      # 质量门（所有小任务必含）
      - cmd: "{项目 lint/测试命令，如 npm run lint / mvn test}"
        desc: "静态检查/单测全通过"
      # 改动集中性（所有小任务必含）
      - cmd: "git cat-file -e {short-hash}^{commit}"
      - cmd: "git show --name-only --pretty=format: {short-hash} | wc -l | tr -d ' ' | awk '{if ($0 <= 15) exit 0; exit 1}'"
        desc: "改动文件 ≤ 15（小任务定义）"
      # 核心产物存在性（根据任务类型自动生成 2-5 条 file_contains）
      - file_contains:
          file: "{新增或修改的关键文件}"
          pattern: "{关键 export / 注册点 / 接口签名}"

# 红线（引用 .claude/knowledge/red-lines.md 对应条目，失败直接 Reject）
red_lines:
  - id: RL-01
    desc: "{本任务相关红线，如'不得使用真人图像'/'Repository 层禁止 Mock'}"
    verify:
      - cmd: "{对应的负向断言}"
```

### 模板裁剪规则

根据本次任务角色（backend/frontend/test/video/doc 等）套用不同的 `verify` 模板片段库：

| 角色 | 必含 verify |
|------|------------|
| backend | mvn test / gradle test + file_contains (controller/service 签名) + sql 断言（若涉及表） |
| frontend | npm run lint + file_contains (组件导出) + cmd (tsc) |
| video (Remotion) | npm run lint + file_contains (Composition 注册 / 场景导出) + cmd (duration 总和校验) |
| test | 仅跑新增测试 + 覆盖率阈值 |
| doc | markdownlint + 关键章节存在性 |

### Step 6.5 的执行流程

```
6.5 最小合同生成（仅小任务）
  ├── 判断 docs/tasks/{sprint}/ 是否存在
  │     ├── 否 → 全量生成三个文件
  │     └── 是 → 只追加本次 T{N+1} 到 tasks.yaml，其他文件不动
  ├── 跑一遍新 T{N+1} 的所有 verify（dry-run）
  │     ├── 全绿 → 继续
  │     └── 有红 → 自愈修断言（≤2 轮）；仍失败则在 T{N+1} 加注释 "dry-run-failed"
  └── 提示："已生成 {sprint}/tasks.yaml 供 /adversarial-review 使用"
```

### 与大任务分支的关系

- 大任务仍由 /iterate 产出完整版 tasks.yaml；Step 6.5 不介入大任务
- 若同一 sprint 内既有 /iterate 又有 /impl 的产物，/impl 自动追加 task 到既有 tasks.yaml，不冲突
